# Fink! Infrastructure

## 1. 프로젝트 소개

Fink!는 금융기업의 내외부 통합 업무 시스템과
보안 접근제어를 모의 구현하는 교육 프로젝트이다.

AWS 기반 네트워크 환경을 구축하고,
인가된 사용자와 서비스만 내부 업무 시스템에
접근할 수 있도록 구성하는 것을 목표로 한다.

## 2. 개발 환경

- OS: Windows
- IDE: VS Code
- Terminal: PowerShell
- Git Branch: hyunmin
- Cloud: AWS
- Java: 17

## 3. 사용 예정 기술

| 기술 | 사용 목적 |
| --- | --- |
| AWS VPC | 독립적인 가상 네트워크 구성 |
| Subnet | 업무 영역별 네트워크 구분 |
| CIDR | IP 주소 대역 정의 |
| Route Table | 네트워크 통신 경로 설정 |
| Internet Gateway | 인터넷 연결 경로 제공 |
| EC2 | 서비스 실행 환경 구축 |
| Security Group | 서버별 네트워크 접근제어 |
| VPN | 인가된 직원의 내부망 접속 |
| IAM | AWS 리소스 접근 권한 관리 |
| Message Queue | 내외부 업무 데이터 연계 |

세부 제품 및 리소스 구성은 설계 단계에서 확정한다.

| --- | --- | --- |
| external-server | Spring Boot | 8080 |

- 임시 회원 및 계좌 데이터 사용

현재 구현은 최종 보안 아키텍처와 구분한다.

## 5. 목표 네트워크 아키텍처

아래는 사용자가 승인한 개발 목표다. 팀 전체의 최종 합의와 실제 구축 여부는 별도로 확인한다.

- VPC 기반 가상 네트워크 구축
- 외부 업무 영역과 내부 업무 영역 구분
- Subnet 및 Route Table 구성
- EC2 기반 서비스 배포
- Security Group 기반 통신 제한
- 직원 전용 VPN 접속 및 별도의 애플리케이션 인증·인가
- 메시지 큐 기반 망연계
- 큐 전환 후 외부 서버의 내부 서버 직접 업무 호출 차단
- IAM 기반 최소 권한 적용
- 내부 금융 원장 DB 직접 접근 제한

CIDR, VPN·큐 제품, 서버 배치, DB 인스턴스, AWS 비용과 세부 통신 정책은 각 설계 단계에서 확정한다.

## 6. 데이터베이스 접근 정책

테이블 정의서에서 DB1(1–8쪽), DB2(9–12쪽), 시황 DB인 DB3(13–19쪽)의 테이블 1번부터 49번까지와 역할을 대조했다.

| DB | 역할 | 테이블 수 |
| --- | --- | --- |
| DB1 | 내부 금융 원장 | 19 |
| DB2 | 외부 고객 서비스 | 11 |
| DB3 | 외부 시황 분석 | 19 |
| 합계 | | 49 |

### DB1

- 정의서는 내부망 서버2에만 접근을 허용한다.
- 외부 서버의 직접 접근을 차단한다.
- 직원의 직접 DB 접근을 차단한다.
- 정의서의 원장 정책은 조회와 `INSERT`만 허용하며, 변경이나 삭제가 필요한 경우에도 새 기록을 추가한다.
- 실제 DB 권한 설정은 DB 담당자와 협의한다.

### DB2

- 회원 앱(서버1)용 데이터베이스이다.
- `member`, `account`, `ledger`, `incident`는 DB1의 조회용 복제본이고 나머지 테이블은 앱이 직접 쓴다.
- 금전 거래는 DB1 원장 기록을 기준으로 확정한다.
- 내부 원장 정보는 승인된 망연계를 통해 전달받는다.

### DB3

- 직원용 시황 분석·예측 터미널 데이터베이스이다.
- 고객 정보는 없으며, 관리자가 초대한 직원은 자신의 기록만 열람한다.
- 인증 방식과 서비스 계정 권한은 팀 협의를 통해 확정한다.

논리 DB의 구분과 실제 DB 인스턴스 배치는
별개의 설계 사항으로 관리한다.

## 7. 직원 접근제어 정책

직원의 내부 업무 시스템 접근은 다음 단계를 거친다.

1. VPN 접속 자격 검증
2. 내부 업무 시스템 접근
3. 직원 애플리케이션 로그인
4. 직원 역할 및 업무 권한 검증
5. 허용된 업무 수행

VPN 접속이 성공하더라도
애플리케이션 인증 및 인가를 생략하지 않는다.

VPN 사용자의 원장 DB 직접 접근을 제한한다.
`INFRA-04`에서는 VPN 접속·인증과 내부 서비스 접근 권한을 확인한다.
실제 원장 DB 접근제어는 DB 연동 후 `INFRA-05`에서 확인하고 `INFRA-07`에서 다시 검증한다.

등록 PC 관리와 VPN 인증서의 연계 방식은
추후 팀 협의를 통해 확정한다.

## 8. 내외부 업무 연계

현재 외부 서버의 `CoreClient`는 내부 서버를 HTTP로 직접 호출한다.

메시지 큐 기반 망연계를 개발 목표로 유지한다.
팀 전체의 최종 승인, 큐 제품, 통신 방식, 요청·응답 구조와 mTLS 적용 구간은 미확정이다.

- 큐 전환 후 외부 서버에서 내부 서버로 향하는 직접 업무 호출 차단
- 승인된 메시지만 전달
- 서비스별 송수신 권한 구분
- 거래 중복 처리 방지
- 요청 및 처리 결과 추적

기존 API 및 서버 코드 변경이 필요한 경우
담당 팀원과 협의한다.
